# Capabilities: the 86 of the approved release, and where each stands in this build

This file is the source of the inherited rows of **`REGISTER.md`**, the one requirements and evidence register since
R7 (20 Nov 2026), which adds each row's acceptance check from the baseline, its verification level, and every R7
requirement. Edit the rows here; regenerate the register with `node scripts/register.ts --write`. The list is the
baseline's (`docs/research/qed-systems-architect/20261118-release-feature-baseline.md`, section 7.1, F-001 to F-086).

**How to read a row.** *In the wallet* says what the owner can reach in the interface and where the code is; "no"
means it is not there. *Rail* is the status word of the same row in `chain/PARITY.md`, which holds the rail's own
evidence test by test and is not repeated here. *Evidence* names what ran for the wallet's side: a test, as
`` `file` › "the start of its title" ``, or an evidence file, optionally with the start of a step's name. *Status* is
for the product as a whole and starts with one of four words:

- **Verified**: something ran and passed that exercises the capability as the baseline describes it. What narrows
  the claim follows the word.
- **Partly**: part is verified; the missing part is named.
- **Not done**: nothing ran.
- **Owner decision**: the baseline leaves it to the owner; what exists is stated.

A screen that only describes a capability does not count: a row is Verified only if something ran. Where the
wallet's own evidence covers less than the rail's, the row says which part is whose. Nothing here was run against a
public chain or the public deployment. On 20 November an adversarial reviewer (an agent of the same model family)
opened 18 rows against the baseline's acceptance column; eight were marked Verified on evidence that showed less.
Each was either given the test it lacked or moved to Partly. On 24 November (R13, audit item O4) an engineer of the
same model family read the other 68 rows against the code and tests as they stand: each row's claims about screens
(names, headings and labels, searched for in `src/screens/` and `src/app/`), about what a test or evidence file covers
(its title or step found, and for the rows named below its assertions read), and the "not yet" and "no test" statements
(searched for in the code and the tests). Thirty-four rows were changed (some may be among the 18 read before): the Vault's screen names had changed in the
Meridian redesign (24 rows said "Pay and hold", "Standing policy", "Security lab" or "Scenarios and economies"); F-006,
F-009, F-012, F-016 and F-024 described Ask, the protection delay, the number of kinds of instruction and Home's screens
as they were before R12 and R13; F-064 and F-080 named labels that are no longer there; F-019 moved from Partly to
Verified on its browser journeys and 102 of 102 active checks, all with software authenticators. Not done: the
cited tests of the 19 rows that rest on `chain/PARITY.md` alone were not read, nor were the assertions of every other
test; a row that reads "Verified" here has not been re-run against a real model, hardware key, public chain or
institution (NOT VERIFIED). `scripts/capabilities.ts` checks this file (86 rows, each id
once, the rail word equal to `chain/PARITY.md`, every file named present, every quoted test title and evidence step
found); `npm test` runs that check. Rows were written by the orchestrating agent; the 24 November review above is the only other reading of 68 of them.
