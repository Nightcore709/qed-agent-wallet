# Capability matrix (skeleton): global support, eligibility, integrations, verified execution, dependencies

qed-systems-architect, 23 November 2026, for R10 section 8 ("Distinguish: 1. Global architectural support. 2. Legal and
commercial eligibility for a particular user. 3. Implemented integrations and actions. 4. Actually verified execution",
and "Maintain a capability matrix covering jurisdictions, integrations, licensing, data entitlements, supported
actions, actual execution evidence and remaining dependencies"). Companion to `20261123-global-money-model.md`.
A skeleton: every row has columns (1), (3), (4) and (5) filled from the code and the register at `b022271`; column (2)
is a join key into the jurisdiction matrix, which qed-fin-infra-compliance is writing now
(`docs/research/qed-fin-infra-compliance/20261123-jurisdiction-matrix.md`, not present in this worktree; this file does
not write it).

## Columns

1. **Global architectural support**: whether the mechanism works for any currency, instrument, network and region,
   independent of who may use it. **G** generic; **G\*** a generic mechanism with rupee, test-token, India-time or
   release-unit constants inside (the limiting site is named); **L** local by construction; **-** no money involved.
   A row moves from G\* to G when the named migration stage of the design note (section 11) lands.
2. **Legal and commercial eligibility**: for a given user, jurisdiction and partner. Here only a pointer:
   "JM: <topic>" names the row of the jurisdiction matrix that decides it; "JM (pending)" until that matrix exists.
   Decisions already on record are cited where they bind (D-022, D-088, N-008, R7-058).
3. **Implemented integrations and actions**: **chain** = the approved release's contracts on the local Anvil chain
   through the rail (valueless test tokens); **paper** = the server's paper venues, payment rail and ledger;
   **scripted** = the release's scripted economies; **server only** = nothing of value moves; **obs** = live public
   market data, read-only. **Real: none** for every row: no real account, payment provider, broker, exchange, public
   chain or money is integrated (`apps/qed-demo/README.md`, "What is live, what is paper, what is not there";
   D-070). The rail word is the one `chain/PARITY.md` gives the row.
4. **Verified execution**: what actually ran, as `apps/qed-demo/CAPABILITIES.md` records it (status qualifier and
   its first evidence item), or a register entry and evidence id (`apps/qed-demo/REGISTER.md`,
   `docs/shared/EVIDENCE_LEDGER.md`), or **none**. Nothing here ran against a real rail.
5. **Remaining dependencies**: the migration stage that makes the row global (S1 to S8), external dependencies
   (EXT-01, EXT-02, N-008, R7-058), owner decisions and open questions.

How the inherited rows were made: `python3 -I docs/research/qed-systems-architect/checks/20261123-capability-matrix.py
apps/qed-demo/CAPABILITIES.md` copies each row's id, capability, rail word, status and first evidence item exactly,
and adds columns (1), (3) and (5) from a table written by hand in that script after reading the code. **Verified**
(the script asserts 86 rows and one mapping per id). The journey rows were written by hand.
